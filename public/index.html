Passkey demo

Sign up and sign in with your fingerprint, face, phone or a security key. No password exists anywhere in this app.

1. Create an account

Your device makes a key pair. The private key stays with you, and only the public key goes to the server.

2. Sign in

No username to type. The server sends a one-time challenge and your device signs it.

3. Try to cheat

Pretend an attacker captured your last sign-in and sends it again. It should be refused, because every sign-in signs a new challenge.

What the server stores

Everything it holds about you. If this leaked, there would be no password to crack or reuse. It lives in the memory of the running server, so a restart wipes it.

    This demo

    You play the user, and the page shows you what the website's server does behind the scenes.

    Create an account
    Your device makes two matching keys. The private key stays on your device, and the public key goes to the server. It's like giving a website a lock that only your key can open.
    Sign in
    The server sends a random one-time code, called a challenge. After your fingerprint, face or PIN, your device signs it with the private key. The server checks the signature with the public key, so the private key is never sent.
    Try to cheat
    This sends your old signature again, as an attacker might. Each sign-in has a new challenge, so the old signature doesn't match and the server refuses it.
    What the server stores
    Your username, the public key and a few details about the passkey. A public key can't be used to sign in, so there is no password to steal.

    The demo keeps accounts in memory, so it forgets them when the server restarts. It shows passkeys only, and it doesn't use a digital wallet.

    Why it needs a long-running server

    Signing in is a short conversation, not a single message. The server sends a challenge, your device signs it, and the server checks the answer against the challenge it sent. So the server has to remember the challenge between those two messages, and it has to remember your public key until your next visit.

    This demo keeps all of that in the memory of one program that stays running.

    What it remembersFor how longIf it's lost
    Challenge5 minutes, or until it's usedThe step in progress fails, and you start it again
    SessionAbout an hourThe page stops showing your account, but your passkey still works
    Account and public keyUntil the server restartsThe account is gone, and your passkey can't sign in any more

    Serverless hosting doesn't suit this. It can start a fresh copy of the program for each request, so the second message may reach a copy that never saw the first one and has no challenge to check against. Running several copies behind a load balancer has the same problem.

    This comes from how the demo is built, not from passkeys. Passkeys only need storage that lasts between requests. A real app would keep accounts in a database and challenges in a shared store, and it could then run on serverless hosting or across many servers. The Flows tab marks where each of these is needed and how to replace it.

    FIDO

    FIDO stands for Fast IDentity Online. The FIDO Alliance is a group of companies and organisations that writes shared rules for signing in without passwords. The rules are open and free to use.

    Think of it as an agreed design for locks and keys. Because everyone follows the same design, passkeys work across the major operating systems, browsers and password managers.

    Names you may see

    FIDO2
    The standard behind passkeys. It has the two parts below.
    WebAuthn
    How a website talks to your browser. SimpleWebAuthn makes this part easier for developers.
    CTAP
    How your browser talks to a phone or security key.
    Authenticator
    Whatever holds your keys and signs with them, such as your phone, your laptop, a password manager or a security key.

    Passkeys

    A passkey replaces your password. It's a secret kept on your device, and you unlock it the same way you unlock your device: with your fingerprint, face or PIN.

    Your fingerprint or face is not sent to the website. It only unlocks the passkey on your device.

    SituationPasswordPasskey
    Signing inYou type a secret and send it to the siteThe secret stays on your device
    Many sitesPeople often reuse the same oneEach site gets its own, automatically
    Fake websiteYou can be tricked into typing itYour browser won't use it on the wrong site
    Site is hackedPassword data can be stolenThieves get only public keys

    Two kinds of passkey

    Synced
    Copied to your other devices through an account such as iCloud Keychain or Google Password Manager. If you lose your phone, your other devices still have it.
    Device-bound
    Stays on one device, such as a security key. It offers the strongest protection, but you need a backup plan in case you lose it.

    You can see which kind you made in the deviceType field on the Try it tab. multiDevice means it can sync, and singleDevice means it's device-bound. The backedUp field shows whether a synced passkey has been backed up yet.

    Hardware binding

    A key is hardware-bound when it's made inside a secure chip and can't be copied out. The chip does the signing itself, so your apps and even your operating system never see the key. Think of a stamp sealed inside a safe: you pass a document in and it comes back stamped, but the stamp never leaves.

    The chip might be in a security key, or it might be the Secure Enclave in an Apple device or the TPM in a Windows PC.

    Two kinds of binding

    These are easy to mix up, and they do different jobs.

    BindingTies the key toStopsApplies to
    Site bindingOne websiteA fake site using your keyEvery passkey
    Hardware bindingOne physical deviceSomeone copying your keyOnly some passkeys

    How it relates to FIDO

    FIDO writes the rules, and they don't require every key to be hardware-bound. Its main promise, protection from phishing, holds with or without hardware binding, because site binding is what provides it.

    FIDO also tests products. Its certification levels, from L1 to L3+, rate how well an authenticator protects its keys. Software running only on an ordinary operating system can't reach L2, and L3 adds tests against hardware attacks.

    How it relates to passkeys

    The two kinds of passkey differ on exactly this point.

    QuestionSyncedDevice-bound
    Where is the key?In your password manager, which copies it to your devices in encrypted formIn one authenticator, such as a security key
    Can it be copied?Yes, by designNo
    Is it hardware-bound?No, because it has to leave the device to syncYes, if the authenticator keeps it in secure hardware
    What if you lose the device?Your other devices still have itIt's gone, so you need a second passkey
    Does it stop phishing?YesYes

    Device-bound and hardware-bound aren't quite the same. Device-bound means the passkey can't leave its authenticator. It's also hardware-bound when that authenticator keeps it in a secure chip, as a security key does.

    Rule-makers draw the same line. For example, the US guidance NIST SP 800-63B accepts synced passkeys at its middle level, AAL2, but its highest level, AAL3, needs a key that can't be exported.

    How a website can tell

    When a passkey is created, the authenticator reports whether it can sync, and the server stores that as deviceType. That's a claim rather than proof. For proof, a site can ask for attestation, which is a signed statement of the authenticator's make and model.

    This demo doesn't ask. It uses attestationType: 'none', so it takes the authenticator's word.

    Why wallets care more

    Wallets use the same idea as passkeys: a private key, a fresh challenge and a signature. The stakes are higher, though. A copied passkey opens one account, but copied identity data could be used wherever that identity is accepted.

    So the EU wallet framework makes hardware binding mandatory for your core identity data, known as PID. It calls this device binding. The issuer puts a public key in the credential, and the matching private key stays in certified secure hardware called a WSCD, which won't release it. To share the credential, the wallet signs a fresh challenge. A thief who copies the credential can't do that, so the copy is useless.

    A WSCD doesn't have to be in your phone. It can also be a smart card or a secure server called a hardware security module. Other credentials in the wallet don't always need this binding.

    Digital wallets

    A digital wallet is an app that keeps on your phone what you'd keep in a real wallet. Apple Wallet and Google Wallet are well-known examples.

    Payment cards
    Tap your phone to pay.
    Tickets and passes
    Boarding passes, event tickets and loyalty cards.
    Digital ID
    Driving licences, ID cards and diplomas, where your country or issuer supports them. These are called digital credentials. A trusted issuer, such as a government, signs them so that others can check they're real.

    The useful part is that you approve what gets shared, and you can share only what's needed. For example, you could prove you're over 18 without giving your full identity.

    The EU requires its member countries to offer citizens an identity wallet by the end of 2026. FIDO began work on wallets in December 2025, and that work is still in progress.

    A crypto wallet is something else. It holds the keys for cryptocurrency.

    Passkeys and wallets together

    They answer different questions, so one doesn't replace the other.

    A passkey says: "It's me again."
    It proves you own the account, and it tells the site nothing else about you.
    A wallet ID says: "Here's a fact about me, and someone trusted confirms it."
    It proves something like your age or your driving licence.

    Example: renting a car online

    1. Sign in to the rental site with a passkey.
    2. Prove you can drive with the digital driving licence in your wallet.
    3. Pay with the card in your wallet.

    On most phones, your passkeys are kept in your password manager, not in the app called Wallet.

    When it needs a long-running server

    Only when one request saves something that a later request has to read. That happens three times in this flow, and the demo keeps all three in the memory of one running program. If a later request reached a different copy of the server, or the server restarted first, the data wouldn't be there.

    On the diagramSaved atRead back atIn a real app
    A. SessionStep 2Every later request, for about an hourA shared store such as Redis, or a signed cookie
    B. ChallengeSteps 6 and 19Steps 12 and 25, within 5 minutesA shared store such as Redis, with a 5-minute expiry
    C. Account and public keyStep 14Step 26, and every sign-in after thatA database such as PostgreSQL

    How to replace it

    1. Move accounts and public keys to a database. Make usernames and credential IDs unique there, so two people can't claim the same name at once.
    2. Move sessions and challenges to a shared store that expires them by itself. That also removes the cleanup timer in server.js.
    3. Read and delete each challenge in one action, so it can only be used once, even if two requests arrive together.

    The server then keeps nothing between requests. Any copy can answer any request, so it can run on serverless hosting or across many servers, and a restart or deploy loses nothing.

    Choose a store where a read always sees the latest write, or step 12 could miss the challenge saved at step 6. A signed cookie can replace the session store, but not the challenge store, because the server couldn't tell whether a challenge had already been used.

    Terms in the diagram

    RP ID
    The site's domain name. RP stands for relying party, which means the website relying on the passkey. This is what site binding ties a passkey to.
    clientDataJSON
    The browser's own note of the challenge and the site address. It's part of what gets signed, so a signature made on a fake site won't pass the checks.
    UP and UV
    Flags from the authenticator. User present means someone was there, and user verified means they passed a fingerprint, face or PIN check. This demo requires both, so a security key needs a PIN or fingerprint set up first.
    User handle
    The user ID saved with the passkey. Together with the credential ID, it lets a passkey say who is signing in, so you don't type a username.
    Counter
    A number the authenticator can raise on each use, which helps reveal a cloned key. Synced passkeys often leave it at 0.
